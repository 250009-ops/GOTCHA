## 1. Executive Summary

**Top findings, ranked by severity:**

1. **Admin self-service profile update does not exist — confirmed.** `apps/admin/src/pages/SettingsPage.tsx` (lines 234–250) renders the admin's name/email/role as **read-only text**, with no input fields, no "Save" button, and no API call of any kind. This isn't a fake/no-op save button — the editing UI was never built. The backend has no matching capability either: `services/api/src/modules/admin/admin.controller.ts` exposes only `GET /admin/me` (line 23); there is **no `PATCH /admin/me` or any admin self-service email/password endpoint** anywhere in `services/api/src`. Verdict: ❌ **Missing feature, not "hardcoded" in the sense of fake success** — there's simply nothing to click.
2. **`AdminUser` is real and used, not dead schema — but only in one narrow place.** Contrary to the initial hint that no references exist, `AdminUser` **is** queried in exactly two places: `auth.service.ts:71` (`issueTokens`, to stamp `adminRole` into the JWT) and `dev-auth.service.ts:267` (dev-bypass login). There is no `AdminController`/`AdminService` CRUD for the `AdminUser` table itself — admin accounts can only be created via `prisma/seed.ts` or a direct Prisma call, exactly as `docs/ARCHITECTURE.md` implies but doesn't state explicitly. A secondary consequence: because the role is baked into the JWT at login time, **promoting/demoting an admin's role does not take effect until they log out and back in** (no live re-check of the `AdminUser` table per-request).
3. **User content moderation is completely bypassed for pasted imports, and the "moderation" admin settings are decorative dead code.** `imports.service.ts:455` sets `publishStatus: PublishStatus.published` directly on paste-imported `ContentItem`s — no `ModerationQueue` row is ever created for user imports anywhere in the codebase (confirmed: `ModerationQueue` is only ever read in `admin.service.ts`, never written to for user-submitted content). Live-tested: after submitting a paste import as the fresh learner, it appeared instantly and globally in `/content/feed` for **all users** (not just the importer), and the admin's "Moderation queue" panel showed **"No pending moderation items"** despite the fresh unreviewed import existing. Additionally, the `contentModerationEnabled` / `autoApproveImports` toggles on the admin Settings page (`apps/admin/src/pages/SettingsPage.tsx:190-205`) save to the DB via `/admin/settings` but are **never read anywhere else in `services/api/src`** — they have zero effect on import behavior. This is the AI-toggle pattern done wrong: contrast with §4 below where the AI-enable toggle **is** correctly enforced server-side.
4. **Reader activity never increments streaks because the frontend calls the wrong of two duplicate "update progress" endpoints.** Two near-identical implementations exist: `reading.service.ts:138-179` (`PUT /reading/progress/:contentId`) calls `streak.recordActivity(...)` at line 177; `content.service.ts:280-314` (`PATCH /content/:id/progress`) does **not** call it. `ReaderPage.tsx:352` calls the latter. Reading time (`totalReadSeconds`) is still tracked correctly, but `streakCount`/`streakLastDate` never update from actual reading — confirmed live and via DB query after a full reading session as the fresh learner.
5. **No onboarding/language-selection flow and no quiz/practice feature exist in the frontend**, despite both being implied by the task brief and (for quizzes) by real backend support. Registration hardcodes `nativeLanguage: 'en'` / `targetLanguages: ['ru']` (`AuthPage.tsx:76-77`) with no UI to choose otherwise. A working `AiService.generateQuiz()` method exists (`ai.service.ts:439`) but has **zero controller route** exposing it (`ai.controller.ts` only defines `POST /ai/lookup`) — it is unreachable dead code, not merely unused by the frontend.
6. **Positive finding:** the admin AI "Enable AI for learners" toggle (`apps/admin/src/pages/SettingsPage.tsx:135-142` → `PATCH /admin/settings` → `AI_SETTING_KEYS.enabled`) is **genuinely enforced server-side** — `ai.service.ts:150-154` (`assertAiAvailable`) throws `ForbiddenException` when disabled, which would correctly block the learner's `/ai/lookup` reader feature. This is the one clear example of a real, working cross-panel admin control.
7. **Positive finding:** admin's Users list and Dashboard correctly reflect fresh accounts live from the DB — both the fresh learner and fresh admin created during this audit appeared immediately in `/users` with accurate per-user data (vocab count, target language, last-active time), confirming that part of the admin↔DB wiring is solid.
8. **The admin Dashboard mislabels real USD revenue as Uzbek soʻm.** `apps/admin/src/lib/utils.ts:22-33` (`formatMoney`) unconditionally formats every number with a `uz-UZ` locale and appends `" soʻm"`, but it's used for genuinely USD figures — Dashboard MRR/revenue (`DashboardPage.tsx:158,162,169`), catalog item prices (`ContentPage.tsx:352,546`), and AI cost figures (`AiUsagePage.tsx:132,133,188`) — even though the backend's own response already includes a `revenueCurrency: 'USD'` field (`admin.service.ts:332`) that the frontend never reads. Confirmed live in this audit's Dashboard screenshot ("Revenue... 12,450 soʻm/mo" is actually a USD import-revenue figure).
9. **`AnalyticsPage` is permanently synthetic, not real-but-currently-sparse data.** Unlike AI Usage (which has genuine live/seed branching with an honest `source` badge), `AdminService.analytics()` (`admin.service.ts:1404-1447`) always computes DAU/session-time/retention/CEFR-distribution/language-distribution/engagement-by-hour purely by scaling static `FIGMA_ADMIN_METRICS.analytics` seed constants by a range multiplier — confirmed by reading the function: it never issues a single real aggregation query against user/session tables. The page has no "demo data" disclosure, unlike AI Usage's badge, so an operator has no way to know this page never reflects real platform activity.
10. **Two Reader features are entirely dead code, not just partially wired.** (a) Resume-to-last-position: `ReaderPage.tsx:240` looks for `item.currentSegmentId`, a field `content.service.ts`'s `getById` never returns — `resumeIdx` is always `-1`, so every book always opens at segment 0 regardless of real saved progress. (b) The Pronounce/TTS button (`ReaderPage.tsx:125-127`) has no `onClick` handler at all — it's permanently inert despite `preferences.ttsEnabled` being a real, persisted user setting.
11. **`apps/admin/src/pages/OpsPages.tsx` is an entire orphaned file** — `LicensesPage`, `ModerationPage`, and `IngestionPage` are exported but never imported or routed anywhere (confirmed via `App.tsx` and a repo-wide reference search); the functionality was superseded by tabs inside `ContentPage.tsx`, but the old file was never deleted.
12. **Admin nav shows sections that 403 for non-superadmin roles, and most pages fail silently into an infinite loading spinner.** `AdminShell.tsx`'s nav array is not filtered by `user.role`, so e.g. a `moderator` sees links to Content/Languages/Level Tests/AI Usage/Gamification/Import & Pricing/Analytics/Settings that all return 403 per the roles declared in `admin.controller.ts`. Nearly every page's data-loading `.catch(console.error)` swallows the error with no fallback UI, so the page is stuck on `<LoadingBlock />` forever for that role — only `DashboardPage.tsx` and `UsersPage.tsx` implement a real retry/error state.

## 3. ADMIN PANEL (`apps/admin`, port 5173)

### 3.1 `AdminUser` model & admin authentication — deep dive

- The `AdminUser` Prisma model (`schema.prisma:715-723`, fields: `userId`, `role` ∈ `{superadmin, editor, moderator, analyst}`) **is real and actively used**, contrary to a "zero references" assumption — it's just used narrowly:
  - `auth.service.ts:71`: on every login/token-issue, `issueTokens` does `this.prisma.adminUser.findUnique({ where: { userId } })` and stamps the resulting `role` into the JWT as `adminRole`.
  - `dev-auth.service.ts:267`: same lookup, for the dev-credential-bypass login path.
  - `common/guards.ts:22-36` (`RolesGuard`) then authorizes every `@Roles(...)`-decorated admin endpoint purely by checking `user.adminRole` **from the JWT**, never re-querying the DB per-request.
- **There is no admin-specific auth controller/service.** Admin accounts are provisioned exactly like regular learner accounts (`POST /auth/register`) and then must be manually elevated by inserting/upserting an `AdminUser` row directly via Prisma — there is no invite endpoint, no admin-registration UI, and no self-serve path. `prisma/seed.ts:184-187` does this for the demo `admin@gotcha.app` account; this audit replicated the same pattern manually for a fresh admin.
- **Consequence confirmed by design (not live-tested further):** because `adminRole` is baked into the JWT at issuance, revoking/changing an admin's role in the DB has no effect until that admin's session token is refreshed/re-issued — there is no live authorization check against the current `AdminUser` row.
- **Admin login UI**: there is no separate admin login form — `apps/admin` redirects unauthenticated users to the web-learner's `/login` with a `returnUrl`/hash-token handoff (`apps/admin/src/lib/auth.tsx`, `consumeHashTokens`), and the login page prefills the seeded admin's credentials whenever `adminReturnUrl` is present (`AuthPage.tsx:23-24`). This works as an intentional shared-auth design, but does mean any user who logs in via that URL is briefly shown admin credentials pre-filled in an otherwise generic-looking login form — worth a security UX look, not a wiring bug.

### 3.2 Admin profile / settings — priority deep dive

**Confirmed precisely, as requested:**

## 5. Frontend ↔ Backend Contract Mismatches

1. **Duplicate "update reading progress" endpoints with divergent side effects** (see Exec Summary #4): `PATCH /content/:id/progress` (`content.controller.ts` → `content.service.ts:280-314`) and `PUT /reading/progress/:contentId` (`reading.controller.ts` → `reading.service.ts:138-179`) accept overlapping/near-identical DTOs but only the latter updates streaks. The frontend is wired to the former. This isn't a missing/extra field mismatch so much as a duplicate-endpoint design hazard that produced a real functional bug.
2. **`generateQuiz` is backend-only dead code** (`ai.service.ts:439`) — no controller route exists to reach it (`ai.controller.ts` exposes only `POST /ai/lookup`). Not callable by any client, web-learner or otherwise, today.
3. **`packages/shared` is not actually imported/consumed by `apps/web-learner`.** `apps/web-learner/src/lib/types.ts:1-15` hand-duplicates `AppLanguage`/`LANGUAGE_META`/`CEFR_LEVELS`/`CONTENT_TYPES` with only a comment ("Keep aligned with… `@gotcha/shared`") rather than an actual import from `packages/shared/src/index.ts`. Low risk today since both copies currently agree, but this is a silent-drift risk — a future update to one will not propagate to the other, and nothing in the build enforces the sync. (`apps/admin/src/lib/utils.ts` does appear to reference the shared package — the drift is specific to web-learner.)
4. **`ModerationQueue` and content-moderation settings are one-directional dead paths**: the Prisma model and admin read-side (`admin.service.ts` — `count`, `findMany`, `findUnique`, `update`) are fully implemented, but nothing in `imports.service.ts` or `content.service.ts` ever inserts a row into it for user-submitted content, so the queue can never have real pending items from the actual import flow that exists today.
5. **Client-side SRS "due" computation** (`VocabularyPage.tsx:275`) duplicates due-date logic that the backend already implements via `GET /vocabulary/review-queue` — a latent-drift risk (the two implementations could disagree on what counts as "due") rather than a hard contract break, since both consume the same underlying `UserVocabulary.nextReviewAt` field.
6. **`ContentItem.currentSegmentId` doesn't exist in the response `ReaderPage.tsx:240` expects it in** — `content.service.ts`'s `getById` never returns this field, so the resume-to-last-position feature is unreachable dead code (see User Panel table).
7. **`ContentItem.knownWordRatio` is expected by `LibraryPage.tsx:129-131` but never produced by any endpoint the Library actually calls** — it's only computed inside `reading.service.ts` (an endpoint the Reader never calls either), so the field is always `undefined` and the "% known" badge branch is unreachable.
8. **`SubscriptionPlan.features` (and `priceLabel`/`priceUnit`/`popular`) are declared in `apps/web-learner/src/lib/types.ts` but have no backing column on the Prisma `SubscriptionPlan` model and are never synthesized by `billing.service.ts`** — always `undefined`, silently triggering a hardcoded 3-item feature-list fallback in Settings.
9. **`ImportPageTier.priceUsd` actually stores UZS, per the schema's own doc-comment** (`schema.prisma:432`: "Amount in UZS (soʻm). Column kept as price_usd for backward compatibility.") — both `admin.service.ts` and `ImportPricingPage.tsx` work around this consistently today, but it's a landmine for anyone who later adds a real USD-denominated price concept and assumes the field name is accurate.
10. **The admin `formatMoney()` helper hardcodes a UZS/soʻm label for what are frequently USD values** (Dashboard revenue, catalog prices, AI cost) — the backend already tells the frontend the correct currency per-field (`revenueCurrency`, `importCurrency`) but nothing reads it.
11. **Most admin write endpoints accept `Record<string, unknown>` instead of a validated DTO** (`admin.controller.ts` — `createContent`, `updateContent`, `createLicense`, `reviewModeration`, `createAchievement`, `updateSettings`, etc., contrasting with the `auth`/`users` modules which do use `class-validator` DTOs) — frontend and backend "agree" on shape only by convention, with no compile-time or request-time contract enforcement for most of the admin surface.
12. **No contract violation found** in the core read/write flows that were checked in depth beyond the above (users/me, vocabulary CRUD, content feed/detail/segments, imports create/list, admin dashboard/users/content/gamification/notifications/support/import-pricing) — request/response shapes sent by the two frontends otherwise match what their respective NestJS controllers/DTOs accept and return, and no frontend call was found targeting a genuinely nonexistent route in this pass.

This is defensible as an admin override/support tool, but the UI doesn't label it that way — it looks like it's toggling a paid subscription state that doesn't otherwise exist.
   - **Dashboard's "Revenue" stat blends two different things.** `admin.service.ts`'s `dashboard()` computes `mrr` from real `UserSubscription` rows (`plan.priceMonthly`) — which only exist because of seed data / the manual "adjust tier" override above, never from an actual purchase — separately from real one-time Atmos import revenue (correctly labeled `importRevenueUzs` / `so'm` on the same screen, e.g. "Imports this month: 500 so'm"). The blended "Revenue $X" figure is **not fake data** (it's a real DB query), but it measures a monetization path (subscriptions) that doesn't functionally exist for users, which will permanently understate/misrepresent the business's actual (import-based) revenue to anyone reading the Dashboard.
   - `services/api/src/modules/billing/billing.service.ts` (`getSubscription`, `enrichPlan`) and `ai.service.ts`'s quota logic still model everything internally as "plan tier" / `aiDailyQuota` / `importLimit" — functionally fine as an internal quota mechanism, but keeps "plan"/"subscription" vocabulary alive throughout the codebase that doesn't match the product's real billing model.
   - None of this blocks real usage today (imports are correctly billed per-Atmos, and no code path attempts to actually charge a monthly card) — it's a **copy/labeling and mental-model consistency issue**, not a functional payment bug, except for the marketing page's false pricing claim.

### 7.3 Library content pricing (admin-set free/paid, distinct from import pricing)

Confirmed this feature **exists on the data/admin side but has zero effect on the learner side** — same conclusion as the prior audit pass, re-confirmed live this round:
- `ContentItem.isFree` / `priceUsd` are real, admin-editable fields (`ContentPage.tsx`'s "Add/Edit Product" form), and `content.service.ts` returns them in the feed/detail responses.
- Nothing in `content.service.ts`'s `getById`/`feed` methods checks `isFree`/`priceUsd` before granting access, and `LibraryPage.tsx`/`ReaderPage.tsx` never render a price or paywall — a learner can open and read a "paid" item exactly like a free one, and `salesCount` never increments anywhere because there's no purchase flow to increment it.
- **New this pass:** discovered the admin's Content → **Pricing tab** ("Bulk Price Generation" — content-type base price, per-page surcharge, and "Buy 3+/Buy 5+" volume-discount toggles, backed by a `catalogPricingRules` platform setting) is **entirely decorative** — confirmed by grep that `catalogPricingRules` is only ever read/written by the admin endpoint that serves this exact tab (`admin.service.ts`) and is never consumed anywhere else in `services/api/src` (not by `content.service.ts`, not by billing). An admin could spend real time configuring "5% off when buying 5+" and it would never affect anything a learner sees or pays. This belongs squarely in the **"extra/unused admin UI"** bucket below.
- **Recommendation (not implemented — scope/risk too large for a same-session fix):** either (a) build the missing learner-side enforcement + an Atmos-style one-time-purchase flow for paid library content (mirroring the import checkout pattern), or (b) if library-content pricing isn't actually planned to launch soon, hide the isFree/priceUsd fields and the entire Pricing tab from the admin UI so operators aren't led to believe this control does something it doesn't.

### 7.4 Fixes made and deployed this session

All three changes below were built, typechecked, and deployed to production (`node scripts/redeploy-frontends.mjs`) during this audit. No backend/API changes, no Atmos code touched, no `git commit` made (matching prior instructions — everything remains part of the same large uncommitted working tree as the previous audit-fix pass).

1. **Import page-tier prices below the Atmos minimum (data fix, not code).** Live production data had the "1–10 pages" and "11–50 pages" import tiers priced at 100 UZS — below the 500 UZS Atmos minimum — which would make `POST /billing/imports/checkout` throw `BadRequestException` for any learner trying to pay for a small import. Fixed by updating the two tiers via the real admin API to 12,000 UZS and 29,000 UZS; re-verified via the `/billing/imports/quote` endpoint that `belowMinimum` is now `false`.
2. **Learner Settings "Upgrade to Premium" card removed** (`apps/web-learner/src/pages/SettingsPage.tsx`) — replaced with a "Usage & Imports" card showing real AI-lookup/import-allowance usage and a button linking to the real Import page, instead of implying a non-existent subscription purchase flow.
3. **Moderator admin role was completely unusable — now fixed.** This was the most significant "mismatched wiring" finding of this pass (see §7.5.3 for full detail): a `moderator`-role admin had backend permission to review the content-moderation queue (`GET/PATCH /admin/moderation`) but the *only* UI path to it (`ContentPage.tsx`'s "User Imports" tab) unconditionally also fetched the curriculum/stats/licenses/ingestion endpoints moderators don't have permission for, and a single 403 among those blocked the entire page behind a hard error screen — with no nav link to it in the first place, and the post-login landing page (Dashboard) also 403'ing for that role. Net effect: **a moderator account could log in and literally never reach any usable screen.** Fixed by:
   - Adding a dedicated "Moderation Queue" nav entry for the `moderator` role pointing straight at `/content/user-imports` (`AdminShell.tsx`).
   - Making `ContentPage.tsx`'s data loading permission-aware: a 403 on the curriculum/stats calls now degrades gracefully (hides the catalog stat cards, "Add Product" button, and non-applicable tabs) instead of blocking the whole page; the licenses/moderation/ingestion calls now load independently (`Promise.allSettled`) so one 403 doesn't blank out the others.
   - Redirecting `moderator` role away from the Dashboard (which 403s for that role) straight to the Moderation Queue on login/home (`App.tsx`).
   - Live-verified end-to-end with a temporary throwaway `moderator` account (created, tested, then deleted): login → lands on Moderation Queue directly, "Approve"/"Reject" buttons work, nav shows exactly Users/Moderation Queue/Support (matching backend `@Roles(...)`), no forbidden-resource screens anywhere in the flow. Re-verified the existing superadmin/editor/analyst experience on the same page is pixel-identical to before (no regression).
   - **api.ts change:** `api()` now attaches the HTTP status code to thrown errors (`err.status`), which `ContentPage.tsx` uses to distinguish "you don't have permission for part of this" from a real failure. This is a small, backwards-compatible addition other pages can reuse for the same pattern.
   - **Known minor remaining gap (not fixed, low severity):** the "Licenses" add-license mini-form still renders on the User Imports tab for moderators even though `POST /admin/licenses` is editor/superadmin-only — a moderator who tries to add a license will get a 403 toast rather than the form being hidden. Left as-is since it doesn't block their core function and hiding it cleanly would require more surgery than was safe to do in this pass.
4. **Cleanup:** the temporary throwaway `moderator` test account was deleted after verification. A test achievement ("Audit Test Badge," now deactivated) and a test notification campaign ("Audit Test Campaign," left in `draft` status, never sent) were created while verifying those flows and could not be deleted via the API (no delete endpoint exists for either) — both are inert but you may want to clear them from the DB directly if you'd like a pristine environment for a demo.

### 7.5 Figma-copy misconnections (as specifically requested)

#### 7.5.1 Extra/unused admin UI (Figma-only, no backend purpose)

- **Content → "Pricing" tab / "Bulk Price Generation" + "Volume Discounts."** Confirmed via grep this entire tab's data (`catalogPricingRules`) is never read by anything except the admin endpoint that serves the same tab back to itself — no learner-facing effect whatsoever (§7.3). This is the clearest example found this pass of UI that exists because a Figma screen existed for it, not because it does anything.
- **Per-item `isFree`/`priceUsd`/"Sales" columns on the Content catalog table** are editable and displayed, but (as above) have no purchase flow behind them — every "Sales" count shown is frozen at whatever the seed data set it to, since nothing increments it. Less purely decorative than the Pricing tab (the fields are at least stored and returned faithfully), but currently has no functional path to ever change from admin-entered values.
- **Dashboard's `mrr`/subscription-plan-distribution metrics** (`admin.service.ts`'s `subscriptions()`, feeding whatever chart consumes "Plan Distribution"/"ARPU"/"ARR") are computed from real `UserSubscription`/`SubscriptionPlan` tables that are structurally sound but functionally only ever populated by seed data or the manual admin "adjust tier" override — there is no self-serve path that would ever grow these numbers organically under the real business model. Not "fake," but modeling a monetization path the product doesn't offer to users.

#### 7.5.2 Missing admin controls (student panel needs it, admin panel lacks it)

- **Library-content paywall enforcement + purchase flow** (§7.3) is the most concrete example: the admin UI to *set* a price exists, but there is no learner-side gate and no purchase mechanism at all — so even if this weren't a missing *admin* control per se, the admin control that exists is functionally incomplete because half the pipeline (checkout) was never built. Filing it here because from the admin's perspective, "mark this content paid" currently has no way to actually be enforced or monetized, which is arguably the more important missing half of this feature.
- No other clear gaps were found in this pass beyond what the prior audit already covered (streak/gamification config **does** exist via the Gamification & Achievements page; notification templates **do** exist via Notifications & Campaigns, though real push/email delivery integration remains unconfirmed as previously noted; feature flags exist in the form of the AI enable/disable + moderation toggles; user role management for *learners* exists via Users page). The one gap that does remain from the original audit — **no admin UI to create/promote/demote other *admin* accounts** (`AdminUser` rows can only be created via `prisma/seed.ts` or direct DB access) — is unchanged from the prior pass and wasn't re-flagged as new, since it's an admin-managing-admins concern rather than something the student panel needs.

#### 7.5.3 Mismatched/broken wiring (admin UI exists but doesn't work correctly)

- **Moderator role was entirely unusable** — the flagship finding of this pass. Full detail and fix in §7.4 item 3. This was a genuine "the backend supports it, the UI doesn't let you reach it" bug, exactly the pattern the user asked to sweep for.
- **Import page-tier prices below Atmos minimum** (§7.4 item 1) — a data-state mismatch rather than a code bug, but had the same practical effect: an admin-configured price silently made real Atmos checkout impossible for small imports until corrected.
- **Learner Settings "Upgrade to Premium" button** (fixed, §7.4 item 2) called a `comingSoon()` no-op toast — a UI element that looked complete and actionable but silently did nothing, consistent with the "mismatched wiring" pattern, now removed rather than left as dead UI.
